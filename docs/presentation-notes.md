## 1. 한 줄 소개

> 여행 조건을 고르면 준비물 목록이 자동으로 만들어지고, 초대 코드로 모인 친구들과 짐을 나눠 맡아 함께 체크하는 웹앱. AWS에 3티어(웹·앱·DB)로 직접 구축했다.

## 2. 이름의 의미 [팀 확인]

PRD에는 이름의 뜻이 적혀 있지 않다. 아래는 화면 컨셉에 맞춘 제안이다.

- **PACK**: ① 짐을 싸다(pack) ② 무리, 한 팀(a pack)
- **QUEST**: 게임의 임무. 준비물 하나하나가 함께 깨는 퀘스트
- **합치면**: "우리 팀이 함께 깨는 짐 싸기 퀘스트". 체크할수록 캐리어가 차오르고 분류를 다 챙기면 배지를 얻는 화면 연출과 이어진다.

## 3. 문제와 해결 (PRD)

| | 내용 |
|---|---|
| 문제 | 단체 여행 준비물이 메신저에 흩어져 있어 누가 무엇을 챙기는지 불분명하고, 중복과 누락이 생긴다 |
| 해결 | 조건별 추천 목록, 담당자 지정, 완료 체크, 팀 진행률을 한 화면에서 함께 본다 |
| 대상 | 준비물을 나눠 챙겨야 하는 모든 여행 그룹(친구, 가족, 동아리 등) |

발표 도입 예시:
> "여행 가기 전 단톡방에서 '선크림 누가 챙겨?', '나 챙길게!' 하다가 결국 두 개 오거나 아무도 안 가져온 적 있으시죠?"

## 4. 기존 방식과 다른 점

특정 앱 이름을 들 때는 발표 전에 그 앱의 기능을 직접 확인한다. 아래는 방식별 비교다.

| 기존 방식 | 아쉬운 점 | PACK QUEST |
|---|---|---|
| 메신저 단톡방 | 대화에 묻혀 누가 무엇을 맡았는지 찾기 어렵다 | 항목마다 담당자가 표시되고 한 화면에 모인다 |
| 공유 메모·스프레드시트 | 목록을 처음부터 직접 써야 하고, 누구나 아무 칸이나 고칠 수 있다 | 조건 4개만 고르면 목록이 자동으로 만들어지고, 체크는 담당자만 할 수 있다(서버가 검사) |
| 개인용 짐 체크리스트 앱 | 혼자 쓰는 목록이라 팀원과 나눠 맡기 어렵다 | 공용 짐은 팀이 나눠 맡고, 개인 짐은 각자 "내 가방"에서 따로 챙긴다 |

PACK QUEST만의 포인트:

1. **조건별 자동 추천**: 국내/해외, 이동수단, 기간, 계절 조합에 따라 목록이 달라진다(FR-02)
2. **공용과 개인 분리**: 여권·칫솔처럼 각자 챙기는 물건은 한 명에게 배정하면 어색해서 분리했다(1일 차 결정)
3. **책임이 분명한 담당자 지정**: 같은 항목을 두 사람이 동시에 맡으면 한 명만 성공하고 다른 사람에게는 "다른 사람이 먼저 맡았어요"가 뜬다. 완료 체크는 맡은 사람만 한다
4. **팀 진행률**: 전체 완료율과 사람별 완료율로 누가 덜 챙겼는지 바로 보인다(FR-06)
5. **가입 없이 코드 하나로 합류**: 이메일·비밀번호 없이 8자리 코드와 닉네임만 있으면 된다 [팀 의견으로 말하기]
6. **설치 없는 웹**: 링크만 열면 휴대폰에서 바로 쓴다(설치형 앱은 PRD에서 제외)
7. **짐 싸는 재미**: 체크할수록 캐리어가 차오르고, 분류를 다 챙기면 배지와 축하 알림이 뜬다(FR-08 화면 연출)

## 5. 핵심 기능 (PRD)

| 번호 | 기능 | 한 줄 설명 |
|---|---|---|
| FR-01 | 여행 생성 | 조건 4개와 닉네임으로 만들고 공유 코드를 받는다 |
| FR-02 | 준비물 추천 | 조건에 맞는 공용 준비물을 분류별로 자동 생성, 개인 준비물은 "내 가방" |
| FR-03 | 코드로 참여 | 공유 코드와 닉네임으로 입장 |
| FR-04 | 준비물 관리 | 항목 추가·삭제, 다른 참여자 화면에도 반영(5초 폴링) |
| FR-05 | 담당자·완료 체크 | 참여자는 자기에게만, 주최자는 다른 사람에게도 배정 |
| FR-06 | 팀 진행률 | 전체와 사람별 완료율(공용 준비물만 계산) |
| FR-07 | 여행 삭제 | 주최자가 여행과 관련 데이터를 모두 삭제 |
| FR-08(선택) | 캐리어 완성도 | 진행률만큼 캐리어가 차오르고 분류별 배지. 새 API 없이 화면에서 계산. 진행 여부는 3일 차 저녁 팀 결정 |

## 7. 라이브 데모 흐름 (초안, 4일 차에 대본 확정)

| 순서 | 누가 | 무엇을 보여주나 |
|---|---|---|
| 1 | 발표자(주최자, PC 일반 창) | 조건을 골라 여행 만들기 → 추천 목록과 초대 코드 |
| 2 | 발표자 | 초대 코드와 QR을 화면에 띄워 청중 합류 |
| 3 | 팀원·청중(휴대폰) | 코드로 합류 → 크루 목록에 이름이 늘어난다 |
| 4 | 팀원 | "내가 챙길게"로 맡기, 같은 항목 동시에 맡기(한 명만 성공) |
| 5 | 팀원 | 완료 체크 → 5초 안에 발표자 화면의 진행률과 캐리어가 오른다 |
| 6 | 발표자 | 분류 완료 배지·축하 알림, "내 가방" 탭(개인 준비물) |
| 7 | 발표자 | 여행 삭제 → 팀원 화면이 입장 화면으로 돌아간다 |

데모 주의:

- 주최자는 **일반 창**에서 만들고 데모 내내 **같은 브라우저**를 쓴다(토큰을 잃으면 주최자 권한도 잃는다)
- 데모 중 브라우저 기록 삭제, 시크릿 창 닫기를 하지 않는다
- 실패하면 백업 영상으로 넘어간다(4일 차 녹화)

## 8. 3티어 아키텍처 (PRD)

```
브라우저(휴대폰·PC)
   │ HTTPS, CloudFront 도메인 하나
CloudFront ──(화면 파일)──▶ S3 (비공개 버킷, OAC)
   │ /api/*  (VPC 오리진)
┌──────────────── VPC ────────────────┐
│ 프라이빗 서브넷                       │
│   EC2 FastAPI ──3306──▶ EC2 MariaDB  │
│ 퍼블릭 서브넷                         │
│   NAT Gateway ──▶ 인터넷(패키지, GitHub, SSM) │
└─────────────────────────────────────┘
```

| 계층 | 구성 | 포인트 |
|---|---|---|
| 웹 | S3 + CloudFront | S3는 비공개, CloudFront(OAC)로만 접근. 화면과 API가 같은 도메인이라 CORS를 열지 않는다 |
| 앱 | EC2 + FastAPI | 프라이빗 서브넷, 공인 IP 없음. CloudFront VPC 오리진에서 오는 요청만 받는다 |
| DB | EC2 + MariaDB 직접 설치 | 프라이빗 서브넷, 앱 서버에서 오는 3306만 허용 |

- 인터넷에서 서버로 들어오는 길은 **CloudFront 하나뿐**이다
- 두 서버가 밖으로 나가는 길(패키지 설치, GitHub, SSM)은 **NAT Gateway 하나**로 통일했다
- 모든 리소스는 AWS 콘솔에서 직접 만들었다(IaC·CI/CD 없음, 프로젝트 목표가 구축 실습)

## 9. 보안 설계

| 영역 | 한 일 |
|---|---|
| 서버 접속 | SSM Session Manager만 사용. 22번 포트를 열지 않고 키 페어도 만들지 않았다 |
| 서버 노출 | 두 서버 모두 공인 IP 없음. 앱 서버는 CloudFront에서 온 요청만 받는다 |
| DB | 앱 전용 계정(SELECT·INSERT·UPDATE·DELETE만), root 원격 로그인 차단, 3306은 앱 서버에서만 |
| DB 비밀번호 | Parameter Store(SecureString)에 보관, Backend 서버 역할만 그 파라미터를 읽는다. 코드·GitHub에 비밀번호 없음 |
| 화면 저장소 | S3 퍼블릭 액세스 모두 차단, CloudFront(OAC)로만 읽는다 |
| 사용자 권한 | 참여 시 서버가 토큰 발급, DB에는 해시만 저장. 서버가 매 요청 권한을 검사한다 |
| 공유 코드 | 8자리, 헷갈리는 글자 제외(약 8,500억 가지), 합류는 IP당 분당 60회 제한 |
| 개인정보 | 닉네임만 저장. 이메일·전화번호·비밀번호를 받지 않는다 |

**[팀 확인] PRD와 실제가 다른 곳**: PRD 보안 표는 "IAM Identity Center(SSO)로 사람별 로그인, 계정 공유는 하지 않는다"인데, 실제로는 권한 문제로 **IAM 사용자 하나를 A 노트북에서 같이 쓰고 있다**(10/20 팀 결정). 발표에서 "사람별 임시 자격 증명"이라고 말하면 사실과 다르므로, "원래 설계는 SSO였지만 권한 제약으로 공용 계정을 쓰고, 작업 순서를 정해 한 노트북에서만 작업했다"처럼 한계로 솔직하게 말하는 것을 추천한다. 예산 알람도 권한이 없어 만들지 못했다(B 체크리스트).

## 10. 한계와 향후 확장

| 한계 (알고 받아들인 것) | 향후 확장 |
|---|---|
| 로그인이 없어 토큰을 잃으면 되찾을 수 없다 | 회원가입·로그인 |
| 5초 폴링이라 반영이 최대 5초 늦다 | WebSocket 실시간 갱신 |
| 추천이 정해진 규칙표 기반이다 | AI 기반 추천, 날씨 API 연동 |

| 방치된 여행 데이터가 남는다 | 데이터 자동 만료 |
| "내 가방" 체크가 기기에만 남는다 | 개인 준비물 체크를 팀원과 공유 |
| 여행지·출발일이 없다 | 여행지·출발일 입력과 D-Day 표시 |

## 11. 예상 질문과 답

### 토큰과 참여자 구분

**Q. 토큰이 뭔가요?**
로그인 대신 쓰는 "이 여행의 입장권"이다. 여행을 만들거나 합류할 때 서버가 한 번 발급한다. 사람마다·여행마다 하나이고, 주최자도 같은 방식의 토큰을 받는다(주최자 여부는 DB의 `is_host`로 구분).

**Q. 토큰은 어디에 저장되나요?**
서버는 원문이 아니라 SHA-256 해시만 DB에 저장한다. 원문은 발급 응답에 한 번만 담는다. 브라우저는 `localStorage`에 `packquest:<공유 코드>` 키로 저장해서 새로고침해도 같은 사람으로 남는다.

**Q. 토큰은 어떻게 서버로 가나요?**
모든 요청의 `X-Pack-Token` 헤더에 담는다. `Authorization` 헤더는 CloudFront에서 캐시 정책과 엮여 따로 취급되므로, 서버까지 확실히 전달되게 사용자 지정 헤더를 썼다.

**Q. 같은 브라우저로 같은 코드에 다시 들어가면요?**
새로 합류하지 않고 기존 사람(예: 주최자)으로 열린다. 그 여행의 토큰이 이미 있으면 그 토큰을 쓴다. 한 브라우저가 같은 여행에 두 사람으로 들어가면 토큰이 엉키므로 일부러 막았다.

**Q. 한 PC에서 팀원 역할을 테스트하려면요?**
시크릿 창, 다른 브라우저, 다른 기기를 쓴다. 저장 공간(localStorage)이 따로라 새 사람으로 들어간다.

| 상황 | 결과 |
|---|---|
| 같은 브라우저 새 탭, 새로고침 | 같은 사람 |
| 시크릿 창 | 다른 사람 |
| 다른 브라우저(Chrome ↔ Edge) | 다른 사람 |
| 다른 휴대폰·PC | 다른 사람 |

**Q. 시크릿 창을 닫으면요?**
토큰이 사라져 그 참여자로 다시 들어갈 수 없다. 같은 닉네임은 이미 그 여행에 있어서(`NICKNAME_TAKEN`) 다른 닉네임으로 새로 합류해야 한다. 시크릿 창에서 여행을 만들었다면 창을 닫는 순간 주최자 권한(항목·여행 삭제)도 잃는다.

**Q. 브라우저 기록을 지우거나 휴대폰을 바꾸면요?**
토큰을 되찾을 수 없다. API 명세에 적어 두고 받아들인 MVP 한계다. 해결은 향후 확장의 로그인이다.

### 로그인

**Q. 왜 로그인 기능을 만들지 않았나요?**
> "5일 MVP라서 핵심 기능 7가지에 집중하고 로그인은 범위에서 뺐습니다. 대신 여행을 만들거나 합류할 때 서버가 토큰을 발급해서, 누가 무엇을 바꿀 수 있는지 서버가 그 토큰으로 검사합니다. 처음부터 로그인으로 교체할 수 있게 설계했고, 회원가입·로그인이 향후 확장 1순위입니다."

덧붙이면 좋은 점: 저장하는 개인정보가 닉네임뿐이라 비밀번호 유출 위험 자체가 없다. 로그인이 없는 대신 추측하기 어려운 코드, 요청 제한, 서버 권한 검사, 토큰 해시 저장으로 보안을 챙겼다.

피해야 할 답: "시간이 없어서 못 했어요" → "범위를 정해서 뺐고, 교체할 수 있게 설계했다"로 말한다.

**Q. 로그인을 붙이려면 무엇이 바뀌나요?**
화면만으로는 안 되고 세 명의 작업이 모두 바뀐다. 서버에 회원가입·로그인 API와 사용자 테이블을 추가하고, 지금 토큰으로 하던 권한 검사를 계정 기준으로 바꾼다. 권한 규칙은 이미 "누가 요청했는지"를 기준으로 만들어 둬서, 그 "누가"를 확인하는 방법만 바꾸면 된다.

### 보안

**Q. 공유 코드만 알면 아무나 들어올 수 있나요?**
그렇다. 공유 코드가 초대장이다. 대신 맞혀서 들어오기는 사실상 불가능하다. 8자리에 헷갈리는 글자(0, O, 1, I, L)를 뺀 31종 글자라 약 8,500억 가지이고, 합류는 IP당 분당 60회로 제한한다. 여행 만들기는 IP당 분당 10회로 제한해 대량 생성을 막는다.

**Q. 제한이 없는 조회 API로 코드를 찔러 보면요?**
토큰이 필요한 API는 토큰부터 검사하고, 틀리면 여행이 있는지는 알려 주지 않고 `TOKEN_INVALID`만 준다. 그래서 조회 API로는 코드를 대입해 볼 수 없다.

**Q. DB가 털리면 토큰도 털리나요?**
DB에는 해시만 있어서 원문 토큰을 알 수 없다.

**Q. 남의 토큰으로 남의 항목을 바꿀 수 있나요?**
토큰은 발급된 그 여행 안에서만 통한다. 항목도 그 여행의 항목인지 서버가 확인한다. 통신은 CloudFront HTTPS다.

**Q. 화면에서 버튼만 숨긴 거 아닌가요?**
아니다. 서버가 매 요청 권한을 다시 검사한다. 버튼 숨김은 사용 편의다.

| 하는 일 | 참여자 | 주최자 |
|---|---|---|
| 조회, 항목 추가, 비어 있는 항목 맡기, 내 담당 해제 | 가능 | 가능 |
| 다른 사람에게 배정, 다른 사람 담당 해제 | 불가 | 가능 |
| 완료 체크 | 자기 담당만 | 자기 담당만 |
| 항목 삭제, 여행 삭제 | 불가 | 가능 |

**Q. localStorage에 토큰을 두면 위험하지 않나요?**
같은 사이트의 스크립트가 읽을 수 있어서 악성 스크립트를 끼워 넣는 공격(XSS)이 주된 위험이다. 화면은 사용자 입력(닉네임, 물건 이름)을 `textContent`로만 넣고 `innerHTML`을 쓰지 않아 입력값이 코드로 실행되지 않는다. 토큰이 털려도 피해 범위는 그 여행 하나이고, 결제나 개인정보는 없다.

### 기능

**Q. 조건에 따라 준비물이 정말 달라지나요?**
그렇다. 위 6번 표대로 공통 목록에 조건별 목록을 더한다. 해외·비행기·1~2박·여름이면 공용 22개, 국내·자동차·당일·겨울이면 16개다(FR-02 인수 기준 "조건을 바꾸면 추가되는 항목이 달라진다").

**Q. "내 가방"은 왜 팀원에게 안 보이나요?**
칫솔·여권처럼 각자 챙기는 물건은 담당을 나눌 필요가 없어 서버에 두지 않았다. 체크는 그 기기 브라우저에만 저장되고 팀 진행률에도 들어가지 않는다(FR-02, FR-06).

**Q. 실시간인가요?**
5초마다 서버에 다시 물어보는 폴링 방식이다. 다른 사람의 체크가 최대 5초 뒤에 보인다. 실시간(WebSocket)은 향후 확장이다.

**Q. 여행을 삭제하면 어떻게 되나요?**
참여자와 준비물이 DB에서 함께 지워지고 모든 토큰도 무효가 된다. 다른 사람 화면은 다음 폴링 때 입장 화면으로 돌아간다. 같은 코드로 다시 합류하면 "여행을 찾을 수 없어요"가 나온다.

**Q. `?mock=1`은 뭔가요?**
서버 없이 화면을 개발하려고 만든 가짜 서버다. 실제 주소에서는 붙이지 않으면 동작하지 않는다. 가짜 데이터가 그 브라우저(일반 창)에만 있어서 시크릿 창에서는 내가 만든 여행이 보이지 않는다.
